# gbrain 技能系统的第一性原理分析

> 从知识管理引擎的不可再分基础功能出发，推导 50+ 个技能的存在理由、层叠结构和映射关系。
> 为构建你自己的 KM 技能套件提供功能性分析框架，而非简单的功能列表。

---

## 方法论

第一性原理分析不是分类学。它问的是：

> **"这个系统最基本的不可再分功能是什么？去掉它，系统还能工作吗？"**

对于知识管理引擎，我们从两个方向推导：

**1. 纵轴：信息的生命周期**
信息在系统中经历 6 个阶段，每个阶段都是必要的：

```
产生/到达 → 摄入 → 组织 → 连接 → 检索/综合 → 行动
   ↑                                              │
   └──────────────── 维护（抗熵）──────────────────┘
```

**2. 横轴：元功能**
每个阶段都需要三样东西才能工作：

- **身份**（谁在用、边界在哪）
- **可观测性**（我怎么知道它工作正常）
- **演化能力**（系统如何自我改进）

---

## 五个不可再分功能

### 1. "信息必须进入系统，否则系统为空"

> 去掉了摄入，知识管理系统就是一个空壳。这是最底层的前提。

这个第一性原理直接决定了 gbrain 有 10 个不同的摄入技能。
不是因为它喜欢多功能，而是因为信息的来源有不可约的多样性：

- **用户主动给的** 一个想法 → 需要 `capture`
- **会话中自然产生的** 想法 → 需要 `signal-detector`（并行、不阻塞）
- **外部链接/文章/推文** → 需要 `idea-ingest`（抓取+分析+存档）
- **音视频/PDF/截图** → 需要 `media-ingest`（多模态处理）
- **会议转录** → 需要 `meeting-ingestion`（参与者消歧+时间线合并）
- **语音笔记** → 需要 `voice-note-ingest`（逐字保留，不可 paraphrase）
- **批量归档（Dropbox/邮件导出）** → 需要 `archive-crawler`
- **从其他工具迁移（Obsidian/Notion）** → 需要 `migrate`
- **外部事件推送（短信/Webhook）** → 需要 `webhook-transforms`
- **不知道走哪个入口** → 需要 `ingest`（路由分发器）

这 10 个技能是不可压缩的——你不能用一个"通用摄入"覆盖所有场景，
因为每个来源的处理链（fetch → parse → extract → classify → file）的前几步完全不同。

### 2. "信息必须可检索，否则相当于不存在"

> 存储不是目的，检索才是。这个原则决定了系统的查询能力不可妥协。

gbrain 对应这个原则的方式不是单一的搜索，而是按查询性质分化的技能：

- **明确事实查询**（"关于 X 我们知道什么"） → `query`（混合搜索+综合+引用）
- **开放研究查询**（"研究一下 Y 的最新进展"） → `perplexity-research`（大脑先查+网络查+对比差异）
- **日常状况**（"今天有什么"） → `briefing`（多源汇聚+时间线压制）
- **深度理解**（"读完这本书/文章，针对我当前的问题给出建议"） → `strategic-reading`（问题透镜）
- **书籍分析**（"给我这本书的个性化分章解析"） → `book-mirror`
- **知识图谱查询**（"A 和 B 之间是什么关系"） → 通过 `query` skill 调用 `graph-query`
- **"关于 X 该问谁"** → 通过 `query` skill 调用 `whoknows`

为什么不能用单一搜索解决所有问题？因为混合搜索只能回答"相关片段在哪"，
而一个真正的知识管理系统需要回答"这些片段对我意味着什么"——这需要不同的综合策略。

### 3. "信息必须被组织，否则会变成噪声池"

> 信息的价值密度随组织度指数增长。不组织的信息是"数据沼泽"。

这个原则催生了 gbrain 最厚的技能层：

**分类系统：**
- `repo-architecture` — 决定每一个新页面该放哪
- `brain-taxonomist` — 写之前咨询 schema 包给出的分类建议
- `eiirp` — 工作结束后 7 阶段审计，确保每个产出都落到了正确位置

**Schema 系统：**
- `schema-author` — 演进类型系统（14+ 种规范化页面类型）
- `schema-unify` — 从混乱的自定义类型迁移回规范化类型

**质量门：**
- `frontmatter-guard` — 确保每个页面的 YAML 前置元数据是合法的
- `data-research` — 针对投资者更新、捐赠等结构化数据，用 YAML 配方保证提取一致

这里的关键洞察：组织不是一次性工作。`eiirp` 技能的存在说明"每次工作后的整理"
是独立的不可再分功能——你不能把这个放到建页面的时候做，因为当时你不知道上下文。

### 4. "信息必须被连接，否则孤岛事实失去大部分价值"

> 知识的价值 = 事实的数量 × 事实之间的连接密度。连接为 0 时价值为 0。

gbrain 用 6 个技能包围"连接"这个不可再分功能：

- `brain-ops` — 每次读取都触发 read-enrich-write 循环，自动建立反向链接
- `enrich` — 新实体出现时，自动补充完整背景、时间线、交叉链接
- `article-enrichment` — 原始文章转结构化页面时执行摘要和交叉引用
- `citation-fixer` — 审计跨页面的引用格式一致性
- `concept-synthesis` — 把多个概念存根去重合成成层级知识地图（T1 Canon → T2 Development → T3 Speculation → T4 Riff）
- `idea-lineage` — 追踪单一思想的演化轨迹：首次提及→最佳表述→反转→矛盾→废弃分支→当前活版本

特别值得注意 `concept-synthesis` 和 `idea-lineage` 的分化：前者解决**多个概念的横向整合**，
后者解决**单个概念的纵向追踪**。它们是同一功能（连接）在空间维和时间维的投影，
不可互相替代。

### 5. "系统必须维护自身，否则信息熵必然增加"

> 热力学第二定律适用于知识系统：不维护则必然退化。

这个原则产生的技能反映了维护需要在不同时间尺度和不同深度上执行：

**即时维护（每消息）：**
- `signal-detector` — 每轮会话并行捕捉原始思考和实体提及
- `frontmatter-guard` — 每次写入验证前置元数据

**日常维护（每天）：**
- `maintain` — 反向链接审计、引用审计、归档验证、过时信息检测、孤立页面
- `dream` — 过夜维护周期（sync→extract→embed→synthesize→patterns→consolidate）
- `gbrain-advisor` — 主动建议：版本漂移、待定迁移、卡住的任务、低嵌入覆盖率

**按需维护：**
- `gbrain upgrade` / `gbrain-upgrade skill` — 自我更新
- `smoke-test` — 重启后验证环境完整性
- `publish` — 安全分享（这本质上是维护信任的函数：确认分享出去的内容不含隐私数据）

**关键洞察：** `maintain` 和 `dream` 的关系说明维护有两个独立的杠杆——
`maintain` 是 Agent 可以即时做的检查（读+分析），`dream` 是系统在后台做的结构性修复（写+重计算）。
两者缺一不可。

## 四个元层

以上五个可再分功能都依赖四个横切元层：

### M1. 身份与存在（Setup + Identity）

你无法管理一个不存在的系统。这个元层包含：

| 技能 | 职责 | 第一性原理推导 |
|---|---|---|
| `setup` | 从零创建大脑（PGLite 或 Supabase，5 分钟内验证通过） | 系统必须存在才能被使用 |
| `soul-audit` | 6 阶段交互访谈，生成 SOUL.md（Agent 身份）、USER.md（用户关系）、ACCESS_POLICY.md、HEARTBEAT.md | 系统必须有边界、所有者和使用规则 |
| `cold-start` | Day-one 数据引导：联系人→日历→邮件→对话→社交→归档 | 空大脑比没大脑更危险（用户在空系统上做决策） |

### M2. 运行时运营（Operations）

系统需要调度、持久化、回放能力：

| 技能 | 职责 | 第一性原理推导 |
|---|---|---|
| `cron-scheduler` | 定时任务管理、错峰、静默时间、唤醒覆盖 | 维护必须按时间执行，不能全靠人类触发 |
| `minion-orchestrator` | 提交、监控、转向、暂停/恢复后台作业 | 长时间运行的 LLM/Shell 任务需要可观测性 |
| `reports` | 时间戳报告：保存和按关键词快速查找 | 系统的输出需要持久化和归档 |
| `ask-user` | 可复用的选择门模式（2-4 选项，等待回应） | Agent 不能自己做所有决定 |

### M3. 可观测性（Observability）

你无法改进无法测量的东西：

| 技能 | 职责 | 第一性原理推导 |
|---|---|---|
| `gbrain-advisor` | `gbrain advisor` 结果的 Proactive 解读 | 健康状态的原始数据对用户无意义，需要转化为行动建议 |
| `skillpack-check` | Agent 可读的 JSON 健康报告，带退出码 | 自动化管线需要机器可读的健康快照 |
| `testing` | Skill 验证框架：前置元数据、章节、清单覆盖、MECE 检查 | 技能本身的正确性需要持续验证 |

### M4. 自我演化（Self-Evolution）

系统必须能改进自己：

| 技能 | 职责 | 第一性原理推导 |
|---|---|---|
| `skillify` | 把任意原始功能变成正确技能化、可测试、可解析、可评估的单元 | 新能力需要标准化的发布流程 |
| `skill-creator` | 按一致性标准创建新技能，带 MECE 验证 | 创建新技能的流程本身需要技能化 |
| `skill-optimizer` | 基于 SkillOpt 论文的文本空间优化器，带验证门控（median-of-3 + epsilon） | 技能文本需要持续优化才能保持有效性 |
| `skillpack-harvest` | 将经过验证的技能从宿主仓库提升回 gbrain | 好的技能会产生在任何地方，需要收割流程 |
| `cross-modal-review` | 第二种模型做质量门控，带拒绝路由链 | 单模型的自评价不充分，需要独立视角验证 |
| `schema-author` | 演进活跃的 Schema 包（添加类型、提议新类型、回填 type 字段） | 分类系统需要随知识结构演化 |
| `schema-unify` | 从混乱的自定义类型迁移回规范化 14 类型系统 | 演化有时需要收敛 |
| `functional-area-resolver` | 用功能区域调度条目替换逐技能路由表，文件缩减约 50% | 路由文件本身需要随着技能数量增长而优化 |

**这个元层是最不明显的，但它是整个系统可持续的关键**——没有它，技能系统会因为
数量的增加和质量的衰减而最终崩塌。

## 技能总表：第一性原理映射

### 层 0 — 存在（Being）

| 技能 | 为什么存在（第一性原理） |
|---|---|
| `setup` | 系统必须先存在 |
| `soul-audit` | 系统必须有身份和边界 |
| `cold-start` | 空大脑的初始填充路径必须被引导 |

### 层 1 — 摄入（Ingesting）

| 技能 | 为什么存在（第一性原理） |
|---|---|
| `capture` | 想法必须能被即时保存 |
| `signal-detector` | 会话中自然产生的想法需要被并行捕捉，不阻塞主流程 |
| `ingest` | 多种摄入路径需要统一的路由分发 |
| `idea-ingest` | 链接/文章/推文的处理链是独立的 |
| `media-ingest` | 音视频/PDF 的多模态处理链是独立的 |
| `meeting-ingestion` | 会议转录的参与者消歧和时间线合并是独立的 |
| `voice-note-ingest` | 语音笔记的逐字保留要求是不可协商的 |
| `archive-crawler` | 批量归档的过滤链（Dropbox/B2/邮件导出）是独立的 |
| `migrate` | 从其他工具的迁移路径是多对一的 |
| `webhook-transforms` | 外部事件的推送接收和实体提取是独立的 |

| `schema-author` | 类型系统需要随知识结构演化 |
| `schema-unify` | 演化有时需要收敛回规范 |
| `data-research` | 结构化数据的重复可执行提取需要 YAML 配方 |

### 层 3 — 连接（Connecting）

| 技能 | 为什么存在（第一性原理） |
|---|---|
| `brain-ops` | 每次读取都需要自动建立连接（反向链接、read-enrich-write） |
| `enrich` | 新实体出现时需要一个独立流程补充完整上下文 |
| `article-enrichment` | 文章的结构化转译需要一个独立转换链 |
| `citation-fixer` | 引用的格式一致性需要一个专门审计器 |
| `concept-synthesis` | 多个概念存根的横向整合（化零为整） |
| `idea-lineage` | 单个概念的纵向追踪（深入演化） |

### 层 4 — 检索与综合（Retrieval + Synthesis）

| 技能 | 为什么存在（第一性原理） |
|---|---|
| `query` | 事实性查询需要混合搜索+综合+溯源 |
| `perplexity-research` | 开放研究需要在已知/未知边界上运行 |
| `briefing` | 日常状况需要多源汇聚和优先级排序 |
| `strategic-reading` | 深度理解需要问题透镜映射 |

| `publish` | 知识的输出格式之二（加密 HTML 分享） |
| `query + whoknows` | 专家路由（谁知道什么）是独立的查询类型 |

### 层 5 — 维护（Maintaining）

| 技能 | 为什么存在（第一性原理） |
|---|---|
| `maintain` | 知识系统的熵必须被即时（在对话中）检测 |
| `dream` | 结构性修复需要后台周期（离线）运行 |

|---|---|
| `cron-scheduler` | 定时执行不能被人类触发 |

## 关键洞察

### 1. 技能数量不是随机的

50+ 个技能不是拍脑袋想出来的。它们来自信息在生命周期中经过的每个阶段 × 每个阶段的不可压缩分化。

从第一性原理推导，最小技能数大概是：

| 阶段 | 最小独立技能数 | 原因 |
|---|---|---|
| 摄入 | ~9 | 信息来源种类不可约 |
| 结构化 | ~7 | 类型系统、放置规则、质量门控各有独立逻辑 |
| 连接 | ~6 | 横向整合 vs 纵向追踪、实体 vs 文章 vs 引用 |
| 检索 | ~7 | 查询性质的分化（事实/研究/日常/深度/输出格式） |
| 维护 | ~4 | 即时检测 vs 后台修复 vs 主动建议 vs 版本管理 |
| **核心合计** | **~33** | |
| 元层（演化+运营） | ~11 | 元系统需要自己的维护 |
| **总计** | **~44** | 与 gbrain 实际 ~50 接近 |

多余的 6 个主要是从"用户可能从哪些工具迁移过来"的适配性和"怎么分享输出"的格式多样性来的。

### 2. 技能是"胖"的，每个都是完整的工作流

这不是巧合。每个技能包含：

- 前置元数据（名称、触发器、工具、是否写操作）
- 合同（Contract）— 它保证什么、不保证什么
- 阶段（Phases / Workflow）— 分步骤的执行说明
- 约定引用（Convention refs）— 指向 `skills/conventions/` 中的共享规则

这相当于每个技能就是一个微型的 agent 行为协议。技能的"胖"程度反映了它所封装的工作流复杂性——`capture` 很简单（5 行说明），`eiirp` 很复杂（7 阶段审计）。

### 3. 触发器（Triggers）是路由的原子单位

每个技能的生命力在于它的 trigger 列表——这是它和其他技能的"边界"。
如果两个技能的 trigger 重叠，你会得到竞态调度（两个 Agent 同时处理同一个请求）。

gbrain 用了两种方式解决：

- `signal-detector` 标注为 `always-on` + 并行 spawn，不阻塞主流程
- `ingest` 是一个分发器，检测输入类型后 delegate 给子技能

### 4. 元层是整个系统中最被低估的设计

`skillify`、`skill-creator`、`skill-optimizer`、`skillpack-harvest`、
`cross-modal-review`——这五个技能构成了一个**元技能循环**：

```
原始功能 → skillify（转化） → skill-creator（发布） → 使用（收集数据）
                                              ↑                   │
                                              │  skill-optimizer  │
                                              │  （文本优化）      │
                                              │                   │
                                              └───────────────────┘
                                                                    │
                                                    skillpack-harvest ↓
                                                 （收割到 gbrain 核心）
```

这是 gbrain 技能体系区别于静态技能包的关键特性——它允许系统自我改进。

## 对构建你自己的 KM 技能套件的启示

1. **不要从技能分类开始**。从"我的信息经过哪些不可压缩的阶段？"开始。每个阶段至少对应一个独立技能。

2. **胖技能比薄技能好**。一个技能就是一个完整的工作流。如果你发现一个技能需要读取另一个技能才能知道怎么做，说明它们可以合并。

3. **触发器（Triggers）就是 API**。技能的边界由它能识别的自然语言触发词定义。设计技能时，先写 trigger 列表——它会暴露你最不确定的地方。

4. **在技能套件里内置元技能**。没有演化能力的技能系统会僵化。至少需要 `skillify`（将新功能包装成技能）和 `testing`（验证技能质量）。

5. **读写的偏重决定系统性格**。gbrain 技能中 ~60% 是 read-only 或主要读（query、briefing、maintain），~40% 是 mutating（capture、enrich、eiirp）。这个比例反映了一个健康的 KM 系统——消费远多于生产。

6. **Conventions 层是隐藏的架构骨架**。`skills/conventions/` 中的 cross-cutting 规则（brain-first 查找协议、质量规则、路由约定）是所有技能的共享基础——它们保证了 50 个独立编写的技能行为一致。
